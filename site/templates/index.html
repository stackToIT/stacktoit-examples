StackToIT Examples

Real infrastructure. Real migration assessments. Reviewable STACKIT target plans.

StackToIT reads a Terraform estate and writes a migration package for STACKIT: the assessment of every resource, a Terraform draft of the target, an ordered execution plan and the decisions that are still open. The runs published here were made on public infrastructure-as-code projects, with default options, and are shown exactly as the tool wrote them.

$hero_actions

  1. 1

    Read the source

    The Terraform root, its local and registry modules, variables and the resources they declare. What is decided only at plan time is named, not guessed.

  2. 2

    Assess and map

    Every resource is classified against the STACKIT knowledge base: DIRECT, RECONFIGURE, REPLATFORM, CONTAINERIZE, REDESIGN, MANUAL REVIEW or BLOCKED, with a confidence and the evidence.

  3. 3

    Write the package

    A STACKIT Terraform draft, API steps where Terraform cannot carry a setting, manual steps with an owner, an execution plan and a decision register. Nothing is applied.

How to read these examples

StackToIT keeps its words apart on purpose. The sheets above use them the same way.

Execution-ready
A step the plan can carry out as written, by OpenTofu or a script a person starts. It says nothing about whether anyone should.
Approved
Every decision and default a step rests on has been answered in the decisions file by the customer's architect. No example here is approved: the decision files are published unanswered.
Executed / deployed
Never, on this site. StackToIT has no execute command and these runs touched no cloud.
Migration ready
YES only when no critical setting of the source is left to a manual or refused step. A NO is the normal first answer on a real estate.
Automation-eligible
A unit whose critical settings are all closed. Different from "steps that can run now": a step can be runnable while its unit still waits on a decision.
Refused
A step StackToIT will not write because it cannot prove equivalence. It is listed, with the reason, instead of being approximated.
NOT RUN
A check that did not happen, with the reason. It is neither a pass nor a failure and is never shown as either.
Proposal
Everything in a package. The architect decides; StackToIT lists what there is to decide.
