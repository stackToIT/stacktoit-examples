<details>
<summary>The 1 manual step of WP-04</summary>

#### The step "Remove the migration user stackit_secretsmanager_user.migration of the Secrets…" (`MAN/path/secrets-migration/retire-user`)

- Phase: Security
- What: Remove the migration user stackit_secretsmanager_user.migration of the Secrets Manager instance stackit_secretsmanager_instance.migrated_secrets once the last secret is written and read back: delete its block and its two outputs (stackit_secretsmanager_user_migration_password and stackit_secretsmanager_user_migration_username) from the draft and run tofu apply, so the provider deletes the user. Afterwards the state must not list it (tofu state list shows no stackit_secretsmanager_user.migration) and the instance must list no user of that name; give a workload that reads a secret a user of its own with write_enabled = false, or the instance's role binding.
- Why: The user has write access to the secrets engine of the whole instance, not to one secret, and STACKIT generated its password into the state in plain text (the sensitive output stackit_secretsmanager_user_migration_password). Setting write_enabled = false is no removal: the provider updates that argument in place and has no flag that disables a user, so the user and its password stay. The provider's delete returns without an error when the API answers 403 (terraform-provider-stackit 0.119.0, secretsmanager user resource), so a successful apply alone does not prove that the user is gone: look at the instance's users in the portal or with the ListUsers request. Take the entry out of the state by hand (tofu state rm stackit_secretsmanager_user.migration) only AFTER the user is deleted in the instance, for example when the instance is already gone: removing it from the state alone leaves a user with write access behind. The earlier versions of the state (a versioned backend, backups) still hold the password; once the user is deleted it opens nothing, and while it is kept those versions are secrets.
- Who: Security Architect
- When: Timing to be scheduled by the owner
- Needs: the draft, the state of the draft and the Secrets Manager instance's list of users
- Done when: the block and the two outputs of stackit_secretsmanager_user.migration are gone from the draft, the state lists no such user, and the instance lists no user created for the migration
- Source: `google_secret_manager_secret.django_admin_password`, `google_secret_manager_secret.django_settings`
- After: the step "Read each migrated secret"
- State: not executable — requires a design decision — blocked by `DEC-GEN-CONVERT-API-OPT-IN/google_secret_manager_secret.django_admin_password`; it also comes after the step "Read each migrated secret", a manual prerequisite; and, as the plan states: until this step is done a credential with write access to every secret of the instance exists and its password is in the state
