# OpenTofu steps

Generated by StackToIT from `execution-plan.json`. Nothing in this folder has been run: StackToIT reads and writes files and creates, changes and deletes nothing in any cloud. Every step is carried out by a person, by OpenTofu or by a script of this folder that a person runs. Paths are relative to the output folder.

The draft is in `terraform/`. OpenTofu applies the whole draft at once and orders its blocks by their references itself; the tables list the OpenTofu steps of the plan for review, grouped by who applies them, each group in the plan's order.

The owner of an area is the person who applies it: a step is applied by the owner role the plan names for the category of the source unit its block is written from ("Applied by"), shared infrastructure (a Network Area, an SKE cluster) by the role of that infrastructure, and a file whose blocks belong to two roles is applied by each role for its own blocks (the Work Board lists the same split). A step for which no role follows (its units belong to categories of different roles, or a category names no role) is listed last, with the reason and no role: none is guessed.

**Do not apply yet.** 13 OpenTofu steps wait for a decision (the tables say which). A full apply creates every block of the draft as it stands, theirs included. Apply only when every OpenTofu step of the tables is executable.

## Apply in two runs

These steps need blocks of the draft to exist, and other blocks of the draft must not be created before them, so one run of OpenTofu cannot carry them: the blocks they need are applied first, the steps are completed in this order, then the whole draft is applied.

`execution/deploy.sh` carries this out: it applies a generated root that holds only those blocks (`execution/stages/`), stops at each of the steps below in this order until a person has completed it, then applies the whole draft, all on one state. It stops before the apply, and says why, when it cannot split the draft; a variable no value has been given for stops it at the stage that needs it and names the variable.

- [ ] `MAN/path/module.retail_app_ecs.module.alb.aws_lb.this/target-network/network-of-the-cluster` — manual step (workloads): Once stackit_ske_cluster.retail_app_ecs_cluster exists, give stackit_application_load_balancer.retail_app_ecs_alb_this its network and its targets: var.alb_cluster_network_id from `stackit network list --project-id \<project>` (the network named shoot--\<hash>--\<the name of the cluster>), the addresses of the nodes from `kubectl get nodes -o wide`. — executable once the automated step it comes after has run: it waits for `TF/stackit_ske_cluster.retail_app_ecs_cluster`

  Script for this step: `execution/terraform/fill-cluster-values.sh`, from the output folder, once the cluster exists:

  ```sh
  PROJECT_ID=<project id> KUBECONFIG=<kubeconfig file of the cluster> sh execution/terraform/fill-cluster-values.sh
  ```

  It reads the network SKE made for the cluster (`stackit network list`, the network named `shoot--<hash>--<cluster name>`) and the InternalIP of every node (`kubectl get nodes`), and writes `alb_cluster_network_id`, `alb_target_ips` as lines of `review/target-values.tfvars` (it replaces the line of that name and keeps the others); it creates and changes nothing in STACKIT or in the cluster. Then run StackToIT again on the same output folder and apply the rest below. The addresses of the nodes change when the node pool scales or is updated: after such a change run the script, StackToIT and the apply again, because the targets of the load balancer are the addresses of the moment the script ran. The kubeconfig is fetched as `terraform/handover/cluster-access/kubeconfig.md` says. Until the values file holds the variables, `execution/deploy.sh` stops at the stage that needs them and names them.


The whole draft (`terraform/`) is the last stage of the same flow, once the steps above are done.
